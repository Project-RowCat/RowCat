# 시각 파리티 — 잰 것, 고친 것, 일부러 다른 것

이 문서는 **런타임 증거의 원장**이다. "같아 보인다"가 아니라 *언제 · 어디서 · 무엇으로
재서 · 어떤 값이 나왔는가*를 적는다.

세 가지가 서로 다른 사실이라는 것이 이 문서의 전제다:

```text
정적 파리티     같은 토큰 · 같은 변형 어휘 · 같은 소유 규칙     소스가 답한다
런타임 시각 파리티 실제로 그려진 두 면이 같아 보이는가          **기기와 브라우저만 답한다**
런타임 부드러움   버벅임 없이 그려지고 움직이는가               스크린샷이 답하지 못한다
```

정적 검사는 **첫 줄만** 증명한다. 이 문서의 `PASS`는 둘째 줄에 대한 것이고, 근거 없이
적지 않는다.

**이 원장은 웹 ↔ iOS 네이티브에 대한 것이다.** 안드로이드는 아래 `NOT_VERIFIED`에 그대로
있고, 이 문서의 어느 줄도 그 플랫폼에 대한 주장이 아니다.

## 왜 이 문서가 생겼는가

앞선 패스들은 파리티를 **토큰이 같다 + 소스를 읽었다**로 주장했다. 그 방법이 놓치는
결함의 본보기가 `Input`이다 — 그 파일에는 `minHeight: controlHeight.md`(36)가 **실제로
적혀 있었고** 웹의 `h-9`와 같은 값이었다. 기기에서 재면 **44**였다:

```text
lineHeight 22 + paddingVertical 10 × 2 + borderWidth 1 × 2 = 44   → minHeight 36은 한 번도 묶이지 않았다
```

소스만 읽는 어떤 검사도 이것을 잡지 못한다. 그래서 랩과 이 원장이 있다.

**2026-09-01의 실행이 같은 모양의 결함을 셋 더 찾았다.** 셋 다 소스에서는 옳아 보인다:

```text
Select      value: { flex: 1 }        늘어나지 않는 부모 안에서 값이 통째로 사라진다 → 갈매기만 남는다
표지        <Image source={{ uri }}>  네이티브 이미지 로더는 우리 fetch를 지나지 않는다 → 세션이 필요한 표지가 404
DialogActions  alignItems로 늘릴 수 없다  `Button`이 자기 `alignSelf`를 언제나 적는다 → 조작이 hug로 남는다
```

## 어떻게 재는가

두 앱에 같은 고정값으로 서는 **시각 QA 랩**이 있고, 둘 다 제품 프리미티브를 그대로
그린다(랩 전용 사본을 만들지 않는다 —
`apps/mobile/src/features/visual-lab/visual-lab-boundaries.test.ts`가 그 사실을 잠근다).

```text
고정값   packages/design/src/visual-lab.ts        두 랩이 같은 글자와 같은 사례 이름을 본다
네이티브  apps/mobile/src/features/visual-lab/     /visual-lab · __DEV__에서만 열린다
웹       apps/web/src/features/visual-lab/        /visual-lab · import.meta.env.DEV에서만 열린다
```

실측은 랩이 **화면에 그린다**(네이티브 `onLayout`, 웹 `ResizeObserver` +
`getBoundingClientRect`). 로그로 내보내지 않는 이유는 둘이다 — 이 앱의 제품 경로에는
`console` 호출이 하나도 없고, **화면에 그린 값은 스크린샷에 함께 남아** 측정과 그림이
같은 프레임의 사실이 된다.

⚠️ **랩이 제품과 다른 자리에 프리미티브를 세우면 그 값은 아무것도 말하지 못한다.**
2026-09-01에 `AppBar`가 그랬다 — 네이티브 랩은 그것을 가로 여백이 걸린 스크롤 **안쪽**에
세워 358을 쟀고 웹 랩은 화면 폭 그대로 390을 쟀다. 두 수는 같은 것을 잰 값이 아니었다.
지금은 두 랩 모두 제품과 같은 자리에 세운다(스크롤 내용의 형제).

### 고친 것 ① — `Input`이 형제보다 8pt 높았다 (2026-08-31)

증상은 **줄의 어긋남**이었다. 입력칸·선택 트리거·버튼을 한 줄에 세우면 입력칸만 튀어
올랐고, 폼이 길어질수록 그 차이가 누적됐다.

고친 방향이 요점이다. 높이를 `36`으로 **고정하지 않았다** — 그러면 글자를 키운 기기에서
이름표가 세로로 잘린다. 대신 한 줄에서 `lineHeight`를 걷어내(그 값은 **여러 줄**의
축이다) 자연 높이를 36 아래로 내렸고, `minHeight`가 비로소 자기 일을 한다: 평소에는
36이고 글자가 커지면 그만큼 자란다. 표적은 한 픽셀도 줄지 않았다(`hitSlop`이 44를
지킨다 — `metrics.ts`).

```text
전   base { lineHeight 22, paddingVertical 10 } + single { minHeight 36 }   → 44
후   base { }                                   + single { minHeight 36, paddingVertical 4 }  → 36
     여러 줄만 lines { lineHeight 22, paddingVertical 8 }                    → 웹 textarea의 py-2
```

**그 결정이 2026-09-01에 값을 했다.** 확대 글자에서 이 칸은 57.3으로 자란다 — 고정
높이였다면 그 자리에서 이름이 잘렸을 것이다.

### 고친 것 ② — 컨트롤의 면이 외관을 따르지 않았다 (2026-08-31)

브라우저에서 두 외관을 각각 재서 얻은 계약이다(`getComputedStyle`, 클래스와
`prefers-color-scheme`를 함께 맞춘 뒤):

| | 라이트 | 다크 |
| --- | --- | --- |
| `input` | `transparent` | `input/30` |
| `SelectTrigger` | `transparent` | `input/30` |
| `Button outline` | `background` | `input/30` |

네이티브에는 그 갈림이 **없었고 두 방향으로 어긋났다**:

```text
입력칸          두 외관 모두 input/30   → 라이트에서 웹에 없는 **회색 상자**
선택·아웃라인     두 외관 모두 background → 다크에서 웹에 있는 **면이 사라짐**
```

지금은 테마 층이 그 갈림을 하나로 갖는다(`Theme.fieldSurface`·`Theme.outlineSurface`,
`theme-colors.ts`의 `controlSurfacesFor`). 값이 아니라 **규칙**이 한 곳에 있으므로 두
프로바이더가 각자 삼항을 적을 자리가 없고, `theme.test.ts`의 네 검사가 그 표의 모양을
잠근다. 2026-09-01의 라이트/다크 재확인에서 그대로 유지된다.

### 고친 것 ④ — `Select`의 값이 통째로 사라졌다

**랩의 `Adjacency` 줄이 그림으로 잡은 결함이다.** 웹은 그 자리에 `Save`를 그리는데
네이티브는 갈매기 하나만 있는 빈 상자를 그렸고, 잰 값이 그 사실을 말한다(50.0 ↔ 71.0).

```text
전   value: { flex: 1 }        50.0 = 12 + **0** + 8 + 16 + 12 + 테두리 2
후   value: { flexShrink: 1 }  79.0 = 12 + 글자 + 8 + 16 + 12 + 테두리 2
     트리거에 justifyContent: "space-between"
```

`flex: 1`이 함께 켜는 `flexBasis: 0`이 결함의 전부다 — 늘어나는 부모(세로로 쌓인
도구줄)에서는 옳게 보이지만, **폭이 내용에서 나오는 부모**(가로줄) 안에서는 그 글자가
부모의 폭에 한 픽셀도 기여하지 못하고 남은 폭이 0이라 그대로 사라진다.

값과 갈매기의 자리를 `flex`의 **부수효과**가 만들고 있었다는 것이 두 번째 사실이다.
지금은 그릇이 `justifyContent: "space-between"`으로 그 배치를 직접 말한다 — 웹의
`justify-between`과 같은 자리다.

남은 8pt(79.0 ↔ 71.0)는 눈금의 차이다: 웹은 `pl-2.5 pr-2 gap-1.5`(10·8·6)이고 이 앱은
`space.md`·`space.sm`(12·8)이다. `Button md 폭`과 같은 부류라 아래 「일부러 다른 것」에
있다.

### 고친 것 ⑤ — 세션이 필요한 표지가 앱에서만 404였다

**두 화면을 나란히 놓아야 보이는 종류다.** 같은 계정, 같은 목록, 같은 카드인데 웹은
그림을 그리고 앱은 자리표시자를 그렸다. 서버 로그가 그 사실을 값으로 말한다:

```text
웹    GET /v2/stories/qa-story-5/cover   200      쿠키가 자동으로 실린다
앱    GET /v2/stories/qa-story-5/cover   **404**  그림 로더에는 쿠키가 없다
```

이 앱의 인증은 요청마다 `Cookie` 헤더를 얹어 이뤄지는데(`auth-fetch.ts`),
`<Image source={{ uri }}>`는 그 `fetch`를 쓰지 않고 **네이티브 이미지 로더**가 자기
요청을 만든다. 표지 읽기는 작품 상세와 같은 술어를 지나므로, 세션이 있어야 보이는 표지 —
주인 자신의 **비공개**·보관·운영 숨김 작품 — 가 전부 그 자리에서 404가 됐다. 발견
격자·작품 상세·`발행한 작품` 칸이 동시에 틀렸다.

고친 자리는 둘이고, 둘째가 이 수정의 실질이다:

```text
① 우리 오리진의 그림에만 세션 헤더를 얹는다        lib/auth-image.ts
② **헤더가 확정되기 전에는 요청을 만들지 않는다**   `Image`는 실패한 주소를 기억한다
```

②가 없으면 고친 것이 고쳐지지 않는다. `Image`는 `onError`로 실패한 주소를 기억하고 그
뒤로는 자리표시자만 그리는데, 쿠키가 SecureStore에서 오므로 첫 렌더에는 아직 없다 — 그
사이에 나간 요청이 정확히 지금까지의 404이고, 쿠키가 뒤늦게 도착해도 그림은 영영 돌아오지
않는다. `booting`을 게스트로 접지 않는 것도 같은 축이다(앱을 새로 켤 때마다 첫 화면의
비공개 표지가 자리표시자로 남는 경로가 그것이었다).

### 고친 것 ⑥ — 창의 바닥 조작이 줄을 채우지 않았다

웹의 `DialogFooter`는 좁은 화면에서 `flex-col-reverse`이고, 그 컨테이너의 기본
`align-items: stretch`가 버튼을 창 폭만큼 늘린다(390에서 308.1). 네이티브는 같은 자리에서
hug였다 — 저장 버튼이 창 왼쪽의 작은 알약이었다.

**`alignItems: "stretch"`로는 되지 않는다.** 이 앱의 `Button`은 자기 `alignSelf`를 언제나
적고(`hug` ↔ `fullWidth`) `alignSelf`가 부모의 `alignItems`를 이긴다 — `EmptyState`가
조작을 가운데 세울 때 만난 것과 같은 벽이다. 그래서 늘리는 결정을 **그릇이 자식에게
건넨다**(`DialogActions`가 `fullWidth`를 넘긴다). 호출부 스물셋에 손으로 적지 않는 이유는
다음 창을 만드는 사람이 그 한 줄을 빠뜨리면 그 창만 조용히 옛 모양으로 돌아가기 때문이다.

같은 실행에서 바닥·전체 창의 좌우 여백도 16 → 24로 맞췄다(웹의 `p-6`). `panelCompact`의
주석이 이미 같은 사실을 적어 두었는데, 그 수정이 가운데 상자에만 들어가 있었다.

### 고친 것 ⑦ — 확대 글자에서 `Select`만 자라지 않았다

접근성 글자 배율을 키우면 이 앱의 컨트롤은 전부 자란다(위 표). 트리거만 `height: 36`으로
버티고 있었고, 그러면 커진 값이 상자 안에서 잘린다 — 상자를 지키느라 값을 읽을 수 없게
만드는 거래다. `minHeight`로 바꾸었고 **평소 크기의 값은 한 픽셀도 바뀌지 않았다**(36).

### 고친 것 ⑧ — `Card`의 링이 배치를 차지했다

웹의 카드 경계는 `ring-1`(그림자)이라 레이아웃에 자리를 차지하지 않고, RN에는 `ring`이
없어 `borderWidth: 1`이 그 일을 하고 있었다 — 그 1pt가 위아래로 더해져 같은 내용의 카드가
**72 ↔ 74**였다.

⚠️ **이 원장은 그것을 한동안 "일부러 다른 것"으로 적었고, 그 근거가 틀렸다.** 적혀 있던
문장은 *없애려면 카드의 경계를 지우거나 그림자로 흉내 내야 한다*였는데, 셋째 길이 있다:
**흐름 밖의 층 하나.** 절대 배치한 테두리 한 겹은 배치에 참여하지 않고, 부모의
`overflow: "hidden"`이 그것을 카드의 곡률로 자른다.

```text
전   borderWidth: 1 이 상자에                    74.0
후   position: "absolute" · inset 0 · borderWidth 1   72.0
     pointerEvents="none" — 카드 전체가 눌리는 자리에서 링이 그 누름을 가로채지 않는다
```

`Panel`은 바꾸지 않았다. 그쪽 웹은 **진짜 `border`**라 배치를 차지하는 것이 옳고, 그래서
처음부터 66 ↔ 66이었다.

### 일부러 다른 것 — `INTENTIONAL_PLATFORM_DIFFERENCE`

- **`Button md`가 3.8 넓다**(46.2 ↔ 50.0). 웹의 기본 버튼은 `px-2.5`(10)이고 네이티브는
  `space.md`(12)다. **제품의 진짜 버튼에서는 그 차이가 나타나지 않는다** — 2026-09-01에
  같은 화면의 같은 버튼을 재서 확인했다:

  ```text
  작품 상세의 기본 행동   웹 358(줄 가득)      앱 358(줄 가득)
  프로필의 팔로우        웹 314 × 36          앱 314 × 36
  창의 바닥 조작         웹 308.1             앱 307.7
  ```

  랩의 고립된 기본값만 다르고 호출부는 같다. 간격 눈금에 10을 더하는 것은 이 차이가
  실제 화면에 나타날 때 할 일이다.
- **`Select`가 8 넓다**(71.0 ↔ 79.0). 같은 눈금 차이의 두 번째 자리다(패딩 12 ↔ 10/8,
  간격 8 ↔ 6). 제품의 `Select`는 대부분 줄을 가득 채우므로(도구줄·설정) 그 폭은 부모가
  정한다.
- **`Switch`가 크다**(32×18.4 ↔ 63×28). iOS의 네이티브 스위치이고 그 크기는 플랫폼의
  것이다. **2026-09-01에 랩이 아니라 제품 화면에서 다시 봤다** — 계정 › `콘텐츠 표시`의
  `성인 콘텐츠 표시` 줄이 두 앱에 같은 모양으로 있다:

  ```text
  두 앱 모두   이름표(첫 줄) + 설명(둘째 줄)이 왼쪽 · 컨트롤이 오른쪽 첫 줄에
              줄 높이를 정하는 것은 **두 줄짜리 글**이고 스위치는 그 안에 든다
  ```

  줄 높이를 바꾸지 않고, 글자 위계를 누르지도 않으며, 다른 디자인 시스템으로 읽히지도
  않는다. 손으로 짠 스위치로 바꾸면 role·토글 제스처·켬/끔 낭독을 전부 우리가 지게 되고,
  셋 다 틀려도 조용하다. **바꾸지 않았다.**
- **대화의 메시지 목록이 바닥에 붙는다.** 네이티브는 `inverted` `FlatList`이고(새 줄이
  붙을 때 바닥에 붙어 있는다), 웹은 짧은 대화에서 위에서부터 쌓인다. 대화가 화면을 채운
  뒤로는 두 화면이 같아진다. 이 축을 바꾸는 것은 가상화와 스크롤 기하를 건드리는 일이라
  스크린샷 파리티를 위해 하지 않는다.
- **대화 화면의 머리말이 전역 유틸리티를 갖지 않는다.** 네이티브는 서랍·뒤로가·제목·
  찾기·대화 설정으로 320pt에서 표적 넷을 이미 쓰고 있다(`chat-screen.tsx`의 근거).
- **`Badge`의 기본 변형이 다르다**(네이티브 `secondary` ↔ 웹 `default`). 아래
  「배지의 어휘」 참고 — 이번 실행에서 **호출부를 전부 세었고**, 어긋난 자리는 고쳤다.

## 배지의 어휘 — 호출부를 세어서 얻은 결론

네이티브의 `Badge` 스무 자리 중 **변형을 생략한 여덟**을 웹의 짝과 하나씩 견줬다.

| 자리 | 웹의 짝 | 웹의 변형 | 판정 |
| --- | --- | --- | --- |
| 발견 카드 `비공개` | `story-card-body.tsx` | `secondary` | 같다 |
| 작품 상세 `비공개` | `story-hero.tsx` | `secondary` | 같다 |
| 시작 장면 `기본 도입부` | `start-scene-editor-card.tsx` | `secondary` | 같다 |
| 머리말 `확인 중` | *(없다)* | — | 네이티브 전용 자리표시자 |
| 프로필 `내 프로필` | *(없다)* | — | 네이티브 전용(웹은 그 자리에 `/account` 링크) |
| **`발행한 작품`의 노출 상태** | `creator-work-card.tsx` | **표**(`public: default` · `private: outline` · `archived: secondary`) | **MISMATCH_FIXED** |
| **초안 목록의 `발행함`** | `draft-list.tsx` | **배지가 아니다** | **MISMATCH_FIXED** |

마지막 둘이 이 감사의 수확이다.

- **노출 상태**는 웹이 표로 갈리는데 앱은 셋 다 기본값(`secondary`)으로 그렸다. 목록을
  훑는 눈이 공개된 작품과 보관해 둔 작품을 구별하지 못했다 — 이 칸이 존재하는 이유가
  정확히 그 구별이다. 지금은 같은 표를 갖고(`WORK_VISIBILITY_BADGE`) 그 값을
  `work-visibility-badge.test.ts`가 잠근다.
- **초안 목록의 `발행함`**은 웹이 **배지를 벗은 자리**다(`draft-list.tsx`의 주석이 그
  이유를 적어 두었다: 줄마다 알약이 서면 목록에서 가장 크게 읽히는 것이 상태가 되는데,
  원고를 고르는 눈이 먼저 닿아야 하는 것은 제목이다). 웹은 `발행됨`/`미발행`을 굵기로만
  가르고, 앱은 알약 하나를 그리며 미발행에는 아무것도 그리지 않았다. 지금은 같은 두 낱말이고
  낱말도 웹을 따른다(`발행함` → `발행됨`).

## 빈 상태의 조작 — 자리마다 웹의 짝을 확인했다

`EmptyState`의 조작은 스물두 자리에서 `secondary`로 **박혀 있었고**, 그 값은 웹의 두
갈래 어느 쪽도 아니다. 웹의 `Empty` 호출부를 전부 세면 이렇다:

```text
primary(웹 default)   막다른 화면에서 나가는 길      로그인 · 홈으로 · 대화 목록으로 · 작품 발견하기
outline               상태 옆에 서는 다음 걸음       새 작품 만들기 · 필터 초기화 · 검색어 지우기 · 만들기로 가기
```

`EmptyState`가 `actionVariant?: "primary" | "outline"`을 받고 기본이 `primary`다 — 이 앱의
호출부에서 그쪽이 흔하기 때문이다(탭으로 들어와 로그인하지 않은 채 닿는 화면이 여덟이고
그 여덟은 전부 앞 갈래다). 어휘를 `ButtonVariant` 전부로 열지 않는다: `ghost`·
`destructive`인 빈 상태의 조작은 웹에 하나도 없다.

`outline`으로 옵트인한 자리는 여섯이고, 그 목록이 **양방향으로** 잠겨 있다
(`apps/mobile/src/lib/boundaries.test.ts`) — 한쪽만 적으면 `actionVariant`를 지우는 변경도
아무 데나 더하는 변경도 초록으로 통과한다.

| 네이티브 | 웹의 짝 | 변형 |
| --- | --- | --- |
| 대화 목록 › 검색 0건 | `chat-library-page.tsx` | outline |
| 초안 편집기 › 없는 초안 | `draft-editor-page.tsx` | outline |
| 초안 목록 › 비었음 | `draft-list.tsx` | outline |
| 발견 › 팔로잉 0건 · 필터 0건 | `gallery-empty.tsx` | outline |
| 작품 테스트 › 없는 초안 | `playtest-page.tsx` | outline |
| 그 밖(게스트 여덟 · 대화 목록 비었음) | 없거나 `default` | primary(기본) |

⚠️ 게스트 갈래에는 **웹의 짝이 없다** — 웹은 그 화면들에서 로그인으로 리다이렉트한다
(`beforeLoad`). 짝이 있는 두 자리(대화 목록·페르소나 서재의 `열 수 없습니다`)가 웹에서
`default`이므로 그 모양을 따랐다.

### 고친 것 ③ — 화면 조합 셋 (2026-08-31)

프리미티브가 아니라 **화면이 조립한 모양**이 갈리던 자리 셋이다. 셋 다 웹 쪽으로
맞췄고, 그중 둘은 이 앱 **안에서도** 비일관이었다.

#### 설정 › 기본 색상 프리셋 — 1×4 점에서 2×2 카드로

```text
전   한 줄에 넷 · 칸이 곧 견본(프리셋 배경을 칠한다) · 이름표는 칸 **밖** 아래
     고른 칸만 테두리 2pt  → 프리셋을 바꿀 때마다 격자가 1pt씩 흔들린다
후   두 칸씩 두 줄 · 카드 안에 견본 상자 · 이름표는 카드 **안**
     테두리 두께는 고정이고 색만 갈린다 · 강조는 흐름 밖의 고리 하나
```

웹은 390에서도 `grid-cols-2`이고 각 카드가 *면 막대 + 포인트 막대*의 미니 목업을
그린다(`sm:grid-cols-4`는 640px부터라 이 앱에 오지 않는다). 넷을 한 줄에 세우면 칸
하나가 84pt이고, 그 안의 견본은 프리셋이 무엇인지 말하기에 너무 작았다.

**이름표가 카드 안으로 들어온 것이 구조의 결과다.** 밖에 두던 근거는 *"흰 프리셋의
배경 위에서 읽히지 않는다"*였는데, 견본을 안쪽 상자로 내리면서 그 문제가 사라졌다 —
이 글자가 앉는 면은 프리셋의 배경이 아니라 화면의 면이다.

고른 칸의 강조는 웹의 `ring-2 ring-primary/30`을 흐름 밖의 겹친 테두리로 옮겼다. RN에는
`ring` 축이 없어서 두께를 바꾸면 배치가 움직이는데, 그건 이 저장소가 활성 표시에 대해
이미 여러 번 적어 둔 규칙을 어기는 일이다. **2026-09-01에 `Card`가 같은 길을 갔다**
(고친 것 ⑧).

#### 계정 › 저장 버튼 — 폭과 그림

```text
닉네임   전 hug · size sm · 그림 없음      후 줄을 가득 · size md · save→check
소개     전 hug · size sm · 그림 없음      후 hug     · size md · save→check
```

웹의 닉네임 칸은 좁은 화면에서 `flex-col`이라 **버튼이 줄을 가득 채우고**, 소개 칸은
`flex-wrap`이라 hug다(글자 수가 같은 줄에 선다). 그 비대칭이 웹의 결정이고 이제 두 앱이
같다.

#### 만들기 › 칸 전환 — `Select`에서 탭으로

```text
전   닫힌 Select 하나 · 빈 상태에 상자 없음 · `아직 작품이 없습니다` · 조작 `새 작품`
후   탭 셋(밑줄 표시 · tablist/tab) · 점선 상자 · `아직 초안이 없습니다` · 조작 `새 작품 만들기`
```

같은 앱의 **설정 화면이 이미 탭**이었다 — 남아 있던 것은 웹과의 차이이자 이 앱 안의
비일관이었다. 새 그릇을 만들지 않고 설정의 이동 줄과 같은 층을 쓴다
(`MotionIndicatorGroup shape="underline"`).

### 고친 것 ⑨ — 대화 목록의 줄이 카드였다

```text
웹    ul.divide-y.border-y   실선으로만 나뉜다 · 줄에 테두리도 곡률도 면도 없다 · py-3 · 62.0
전    Card의 모양            테두리 1 · 반경 lg · colors.card · 줄 사이 8pt 간격 · py-2 · 57.0
후    실선                   ItemSeparatorComponent · 목록의 위아래를 닫는 선 · py-3 · 64.0
```

줄 높이는 이미 거의 같았으므로(62 ↔ 57) 그 차이는 밀도가 아니라 **성격**이었다 — 웹은
이어지는 명단이고 이 앱은 떠 있는 카드 더미였다.

⚠️ 이 자리를 지키던 정적 검사는 **방향이 뒤집혔다.** 예전 검사는 그 줄이 둥근 카드라는
전제 위에서 `overflow: "hidden"`을 요구했는데(각진 눌림 배경이 곡률 밖으로 삐져나오는
것을 막는 값이다), 지금은 곡률 자체가 없으므로 그 요구가 성립하지 않는다. 값을 지우는
대신 **없다는 사실을 잠갔다** — 카드 모양은 한 줄이면 돌아오고, 돌아온 그 줄은 리뷰에서
평범한 스타일 추가로 보인다.

### 고친 것 ⑩ — 알림 줄이 7pt 낮고 구분선이 없었다

한 줄에 7pt는 눈에 띄지 않지만 이 화면은 같은 줄이 계속 이어지는 자리라 일곱 줄이면

모양으로** 읽혔다 — 웹은 모든 줄이 같은 사각형이고 읽지 않음은 면의 밝기 하나로만 말한다.

`14`는 눈금 밖이다. 그 수는 이 앱이 고른 리듬이 아니라 **웹이 이미 정한 줄 높이**에서
왔고, 가장 가까운 토큰(12·16)으로 반올림하면 그 계약이 깨진다.

적어 둔 것도 읽지 못했다.

그 뒤 부재가 **판정**이 됐고 정적 스캔이 지켰다(당시 `billing-boundaries.test.ts`의

### 움직임 — 이 실행에서 본 것

`AnimatedLabel`의 빠른 수렴을 프로필의 팔로우 버튼에서 실제로 눌러 봤다

⚠️ **중간 프레임은 이 문서의 주장이 아니다.** 스크린샷은 마지막 상태를 증명할 뿐이고,
그 사이가 매끄러웠는지는 위 `NOT_VERIFIED`에 남는다.

### Release를 짓는 일 — **막고 있던 것과 그 근거**

**2026-09-01에 풀렸다.** 그전까지 이 저장소를 **지금 상태 그대로** Release로 지으면
네이티브 컴파일이 멈췄다:

```text
expo-modules-core@57.0.14/ios/WorkletsAdapter/ExpoWorkletsBridgeProvider.mm:236
  workletRuntime->executeSync(...)
    → no member named 'executeSync' in 'worklets::WorkletRuntime'
```

`WorkletRuntime::executeSync`는 `react-native-worklets` **0.10에 있고 0.12에서
사라졌다.** 그리고 Expo SDK 57의 `expo-modules-core`는 그것을 부른다 — 그 패키지가
선언한 피어 범위가 그 사실을 그대로 적어 두었다:

```text
expo-modules-core@57.0.14   react-native-worklets: ^0.7.4 || ^0.8.0 || ^0.9.0 || ^0.10.0
react-native-reanimated 4.5.1   react-native-worklets: 0.10.x
react-native-reanimated 4.6.0   react-native-worklets: 0.12.x     ← 범위 밖이다
```

**그래서 이것은 "빌드가 깨졌다"가 아니라 "SDK 57이 실을 수 없는 짝을 골랐다"였다.**
`722a15b9`가 Reanimated를 4.6.0으로 올리면서 Worklets가 0.12.1로 따라 올라갔고, 그
조합은 SDK 57의 어느 패치로도 성립하지 않는다(57.0.14가 그 계열의 마지막이다).

되돌린 자리는 **Expo가 스스로 싣는다고 적어 둔 판**이다 — 임의의 하향이 아니다:

```text
expo@57.0.18/bundledNativeModules.json
  react-native-reanimated  4.5.1
  react-native-worklets    0.10.1
```

⚠️ **그래서 이 짝은 손으로 지키지 않는다.** `apps/mobile/src/lib/native-dependencies.test.ts`가
**관계**를 본다: 고정한 판이 설치된 SDK의 `bundledNativeModules`와 같은가, 그 worklets 판이
`expo-modules-core`의 피어 범위 안에 있는가, 그리고 앱과 `@rowcat/ui-native`가 **같은
설치본**을 보는가. 판 번호를 리터럴로 적지 않으므로 SDK가 올라가는 날 이 검사가 그 상승을
막지 않는다.

**이 실패에는 JS 쪽 증상이 하나도 없었다** — 타입도 테스트도 `expo export`도 통과하고,
이미 설치된 Debug 바이너리는 멀쩡히 돌았다(`pod install`은 네이티브를 다시 지을 때만
돈다). 그래서 그 상승은 리뷰에서 평범한 diff로 보였다.

```text
                       있고 이 실행에는 세션이 없었다
AnimatedLabel의 중간 프레임  A→B→A를 **앞 전이가 끝나기 전에** 끊었을 때의 프레임을 재지 못했다.
                       끝 상태(최종 낱말·폭·잘림 없음)는 앞 슬라이스가 확인했고, 갈아 끼우기
                       한 번의 프레임도 쟀다(중앙값 16.7ms) — 재지 못한 것은 **끊긴 전이**다.
                       같은 이유로 로그인이 필요하다
런타임 부드러움           스크린샷은 이것을 증명하지 못한다 — 중간 프레임은 이 문서의 주장이 아니다
```

## 이 원장을 다시 채울 때

```bash
# 웹
pnpm dev                      # /visual-lab
# 네이티브
pnpm --filter @rowcat/mobile ios
xcrun simctl openurl <udid> rowcat://visual-lab
xcrun simctl ui <udid> appearance dark            # 두 외관을 각각 본다
xcrun simctl ui <udid> content_size accessibility-extra-large   # 그리고 확대 글자에서 한 번 더
```

두 랩의 `Measured` 표를 나란히 놓고 위 표를 갱신한다. **한쪽만 보고 채우지 않는다** —
이 문서의 값은 전부 두 값의 쌍이다.

⚠️ **`pod install`이 UTF-8 로케일을 요구한다.** Release 설정으로 처음 빌드할 때 그것이
돌고, 로케일이 없으면 `Encoding::CompatibilityError`로 멈춘다:

```bash
LANG=en_US.UTF-8 npx expo run:ios --configuration Release --device <udid>
```
