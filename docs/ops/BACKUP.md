# 백업 · 복원 · 업그레이드

이 문서가 답하는 것은 셋이다 — **무엇을 지켜야 배포가 되살아나는가, 그것을 어떻게 되돌려 놓는가, 이미지를 바꿀 때
무엇이 되돌릴 수 있고 무엇이 아닌가.** 실행하는 것은 `scripts/backup.sh` · `scripts/restore.sh`이고, 두 스크립트가
실제로 되살리는지는 `scripts/compose-smoke.sh`(CI)와 `scripts/upgrade-smoke.sh`가 매번 확인한다.

## 지켜야 하는 것

```text
Postgres (db-data 볼륨)   배포의 전부. 계정 · 세션 · 작품 · 댓글 · 신고 · 알림 · 첫 실행 상태 · 암호화 동기화 기록,
                         그리고 미디어의 바이트 자체(아바타 · 커버 · 장면 이미지 · 런타임 이미지와 소리)
.env                     BETTER_AUTH_SECRET · POSTGRES_PASSWORD · 운영 설정
```

지키지 않아도 되는 것:

- **Redis** — 속도 제한 카운터와 캐시뿐이다. 비어서 떠도 잃는 것은 지난 몇 분의 카운트다.
- **Caddy의 `caddy-data`**(`HTTPS.md`) — 인증서는 스스로 다시 받는다. 다만 발급 기관의 속도 제한에 걸릴 수 있으니
  지우지 않는 편이 낫다.
- 컨테이너 안의 파일 — 미디어 저장소의 유일한 어댑터가 Postgres라서(`lib/media/postgres-store.ts`) 앱 컨테이너는
  상태를 갖지 않는다.

⚠ **`.env`는 덤프와 짝이다.** `BETTER_AUTH_SECRET`은 세션에 서명하고 **저장된 2FA 비밀도 그 키로 암호화된다.** 다른
키로 복원하면 계정은 남지만 모두가 로그아웃되고, 켜 두었던 인증 앱이 다시는 맞지 않는다(백업 코드도 같이 잠긴다).
`.env`는 덤프와 같은 곳에 두되 따로 암호화한다 — 데이터베이스 비밀번호도 들어 있다.

## 백업

```bash
scripts/backup.sh                 # ./backups/rowcat-<UTC 시각>.dump
scripts/backup.sh /srv/backups    # 다른 디렉터리
```

- **돌아가는 채로 뜬다.** `pg_dump`는 한 MVCC 스냅숏을 읽으므로, API와 백그라운드 작업이 도는 동안에도 파일에는
  한 순간의 데이터베이스가 담긴다(트랜잭션의 절반이 담기는 일은 없다). 작업을 멈출 필요가 없다 — 다만 매일 도는
  작업(기본 03:00, 보존 파기 03:30, `docs/jobs/ARCHITECTURE.md`)과 겹치지 않는 시각을 고르면 부하가 갈린다.
- **덤프는 0600으로 만들어진다.** 이메일, 댓글, 공개 작품의 본문이 평문으로 들어 있다(동기화 기록은 암호문 그대로다).
  서버 밖으로 옮길 때는 암호화한다 — 예: `age -r <공개 키> < file.dump > file.dump.age`.
- **읽히지 않는 덤프는 남기지 않는다.** 스크립트가 `pg_restore --list`로 표 데이터가 있는지 확인한 뒤에야 파일에
  최종 이름을 붙인다.

정기 실행은 호스트의 cron이 한다(저장소에 스케줄러를 하나 더 두지 않는다 — 백업은 배포 바깥의 일이다):

```cron
15 4 * * *  cd /srv/rowcat && scripts/backup.sh /srv/backups >>/var/log/rowcat-backup.log 2>&1
45 4 * * *  find /srv/backups -name 'rowcat-*.dump' -mtime +14 -delete
```

**보존 기간은 배포의 결정이다.** 덤프에는 탈퇴한 회원의 기록도 그 덤프를 뜬 시점의 모습으로 남는다. 백업을 얼마나
두는지는 그 배포의 개인정보 처리 방침이 말하는 보존 기간과 맞춘다 — 위의 14일은 예시다.

## 복원

새 인스턴스나 빈 볼륨에만 복원한다. `restore.sh`는 테이블이 하나라도 있는 데이터베이스를 거절한다 — 살아 있는
데이터 위에 붓는 것은 아무도 고르지 않은 병합이다.

```bash
# 1. 같은 .env를 둔다(BETTER_AUTH_SECRET이 같아야 한다)
# 2. 빈 볼륨 — 옛 볼륨은 복원을 확인할 때까지 지우지 않는다. 다른 서버라면 처음부터 비어 있다.
docker compose down
docker volume rm rowcat_db-data          # ⚠ 이 서버의 현재 데이터를 지운다. 그 데이터의 덤프가 있는지 먼저 본다
# 3. 복원 — db만 띄우고, 비었는지 보고, 붓는다
scripts/restore.sh /srv/backups/rowcat-20261102T041500Z.dump
# 4. 나머지
docker compose up -d --wait
```

- **작업은 복원 직후에 바로 돈다.** 덤프 안에 아직 보내지 않은 푸시가 있으면(수명 24시간) 다시 나간다. 보기 전에
  돌지 않게 하려면 4단계를 `BACKGROUND_JOBS_ENABLED=off`로 띄우고, 확인한 뒤 되돌린다.
- **덤프 뒤에 일어난 일은 되돌려진다.** 그 사이의 가입 · 게시 · 업로드는 사라지고, 그 사이에 탈퇴한 회원은 되살아난다.
  탈퇴는 이용자가 요청한 삭제이고 서버에 그 요청의 흔적은 남지 않는다(삭제가 그 신원을 지운다). 덤프 시점 이후에
  탈퇴를 요청한 사람이 있었다면, 그 요청을 받은 경로(문의 · 메일)에서 찾아 다시 처리한다.
- 복원한 데이터베이스에 첫 관리자가 있으면 첫 실행 설정은 닫힌 채로 뜨고 코드를 찍지 않는다.
- 복원의 확인은 아래 「확인한 것」의 목록이 그대로 체크리스트다.

## 업그레이드

```bash
scripts/backup.sh                                  # 먼저 — 되돌아갈 유일한 길이다(아래 「롤백」)
# .env의 ROWCAT_IMAGE_TAG를 새 판으로(예: sha-<커밋>)
docker compose pull && docker compose up -d --wait
```

- **마이그레이션은 API가 부팅할 때 적용된다**(`apps/api/src/db/migrate.ts`). 적용이 끝나기 전에는 트래픽을 받지
  않는다. 복제본 여럿이 동시에 떠도 drizzle의 기록 표가 한 번만 적용하게 한다.
- **마이그레이션은 앞으로만 간다.** 되돌리는 스크립트(down)는 없다. 저장소의 마이그레이션은 기준선 하나와 그 뒤의
  추가분이다(`apps/api/drizzle/`). 새 판이 마이그레이션을 더하는지는 그 디렉터리의 차이로 미리 본다:
  `git diff --stat <지금 판>..<새 판> -- apps/api/drizzle`.
- 옛 덤프는 새 이미지에서 복원할 수 있다 — 복원한 뒤 첫 부팅이 모자란 마이그레이션을 적용한다.

### 롤백의 경계

```text
옛 이미지 + 업그레이드 전 덤프      지원한다. 업그레이드 뒤에 쓰인 데이터는 잃는다
옛 이미지 + 새 스키마(볼륨 그대로)   지원하지 않는다. 마이그레이션이 없던 판끼리는 우연히 돌 수 있을 뿐이다
새 덤프를 옛 이미지에 복원          지원하지 않는다. 옛 코드가 모르는 표와 열 위에서 돈다
```

그래서 업그레이드 전 백업은 선택이 아니다 — 새 판에 문제가 있을 때 돌아갈 곳은 그 덤프뿐이다.

## 서버가 되살릴 수 없는 것 — 기기의 데이터와 열쇠

대화와 초안의 원본은 **기기**(웹은 IndexedDB, 앱은 SQLite)에 있다. 서버에 있는 것은 동기화를 켠 회원이 올린
**암호문**과, 그 회원의 복구 코드로만 열리는 열쇠 묶음(keyring)뿐이다.

- **동기화를 켠 적 없는 회원의 대화와 초안은 어느 백업에도 없다.** 서버가 받은 적이 없다.
- **백업은 암호문을 그대로 되살린다** — 복원된 배포에서 같은 기기는 그대로 이어서 동기화하고, 새 기기는 복구 코드나
  페어링으로 들어온다(아래 확인한 것).
- **열쇠를 모두 잃으면 운영자도 열 수 없다.** 모든 기기의 기억된 키와 복구 코드를 함께 잃은 회원의 기록은 백업이
  있어도 읽을 수 없다. 서버는 그 키를 가진 적이 없고, 백업에서 꺼낼 수 있는 것도 없다. 그 회원이 할 수 있는 일은 동기화
  초기화(암호문을 지우고 새로 시작) 하나다.
- **기기에만 사는 값**(AI 제공자 키, 모델 선택 같은 기기 설정)은 동기화되지도, 백업되지도 않는다.

## 확인한 것

2026-11-02, Docker 29.7 · Compose 5.4 · Postgres 18(alpine), macOS arm64. 이미지는 각 ref에서 구웠다(GHCR 이미지는
익명으로 받아지지 않았다 — `CLEAN-INSTALL.md`).

**백업과 복원** — `scripts/compose-smoke.sh`의 「backup and restore」(CI가 매번 돈다). 돌아가는 스택을 덤프하고,
볼륨을 지우고, 빈 볼륨에 복원한 뒤 물었다.

```text
덤프                                  0600, pg_restore --list로 읽힌다
데이터가 있는 데이터베이스로의 복원     거절된다
첫 실행 설정                           닫힌 채, 새 코드를 찍지 않는다
관리자 세션                            복원 전에 받은 쿠키가 그대로 통한다
작품                                  손님의 갤러리에 있다
커버 · 아바타                          SHA-256이 복원 전과 같다
동기화(apps/mcp/scripts/sync-fixture.ts)
  keyring                             복구 코드가 같은 키로 연다, 소유 증명을 서버가 받는다
  암호화 기록 세 개                    그대로 내려오고 올린 평문으로 풀린다
  페어링                               새 기기가 릴레이로 같은 키를 받는다
```

**업그레이드** — `scripts/upgrade-smoke.sh <이전 ref>`. 이전 판의 API로 채우고, 백업하고, 같은 볼륨에서 새 판으로
바꾼 뒤 위와 같은 것을 물었다.

```text
desktop-2026-10-31(a780871) → HEAD(577c580)   마이그레이션 4 → 4   전부 통과
1bdf364(공개 루트)           → HEAD(577c580)   마이그레이션 2 → 4   전부 통과 — 데이터 위에서 두 마이그레이션이 적용됐다
```

공개된 판의 태그가 아직 하나뿐이라(`desktop-2026-10-31`) 마이그레이션을 건너는 경우는 공개 루트에서 쟀다. 릴리스마다
직전 태그에서 이 스크립트를 한 번 돌린다.

확인하지 못한 것: 실제 복수 복제본에서의 동시 마이그레이션(컴포즈는 API 하나다), 기기 쪽 앱이 복원된 서버로 자동
동기화를 이어 가는 모습(위의 기록 · 페어링은 같은 프로토콜을 쓰는 헤드리스 기기로 확인했다).
