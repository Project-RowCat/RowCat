# 크리에이터 런타임 발행

**저작 소스가 실행 가능한 아티팩트가 되는 한 번의 경계.** Phase 7이 만든 것이고, 그
경계에서 가장 중요한 문장은 하나다 — **서버가 컴파일의 권위다.**

```text
초안(기기)                             로컬 우선 · E2EE 동기화 · 편집 가능
  └ DraftRuntimeProject + DraftRuntimeFile[]
        │  prepareStoryPublication   정규화(삭제 제외 · 경로순 · 진입점 확인)
        ▼
발행 요청의 runtime 필드               **소스**가 실린다 — 아티팩트가 아니다
        │  POST/PUT /v2/stories
        ▼
API                                    모양·상한 검사 → @rowcat/runtime-compiler → 아티팩트 검증
        ▼
story_runtime                          불변 실행 스냅샷 하나
```

## 1. 세 층이 다른 것이다

이 슬라이스에서 가장 자주 헷갈리는 자리라 먼저 적는다.

```text
제작자 소스        기기의 저작 레코드      E2EE 동기화 · 편집 가능 · 서버가 읽지 못한다
발행 아티팩트      서버의 발행 데이터       불변 · 인가받은 플레이어가 내려받는다
플레이어 저장      회원의 사적 데이터       로컬 우선 · E2EE 동기화 · 서버에 불투명
```

가운데만 서버가 평문으로 갖고, 그것이 **의도다** — 그 값은 실행되어야 하고, 실행하는
것은 플레이어의 기기다.

## 2. 서버가 다시 컴파일한다

클라이언트가 만든 아티팩트를 발행 입력으로 받지 않는다. 계약에 그 자리가 **없다**
(`StoryPublishRuntimeInput`).

근거는 하나다: 클라이언트가 만든 아티팩트는 그것이 RowCat 컴파일러의 정책 계층을 지났다는
것을 **아무것도 증명하지 못한다.**

```text
import 제한 · 동적 코드 제한 · 모듈 그래프 검증 · 진입점 형 검사 · 컴파일러 진단
```

그 다섯이 전부 브라우저 안에서 일어났고, 브라우저를 쓰지 않는 HTTP 클라이언트 하나면 그
층 전체가 없는 것이 된다.

**⚠️ 그래도 샌드박스가 1차 보안 경계다.** 여기서 컴파일을 요구하는 것은 격리를 대신하는
것이 아니라, 발행이 **일부러** 정책 계층을 건너뛰지 않게 하는 것이다. 우회로는 여전히
있고(`globalThis["ev"+"al"]`), 실제 격리는 실행 시점의 WASM VM이 한다. "서버가
컴파일하니 안전하다"는 문장을 코드에도 제품 문구에도 적지 않는다.

## 3. ⚠️ 발행된 런타임 코드는 비밀이 아니다

컴파일된 아티팩트는 인가받은 플레이어의 **기기에서 실행된다.** 그러므로 기술적으로 열어
볼 수 있다:

```text
내려받은 컴파일 모듈 · 문자열 리터럴 · 인물 지시문 · 제어 흐름
```

`promptProtected`가 이것을 바꾸지 않는다 — 그 플래그는 **대화 재생 스냅샷**의 축이고,
클라이언트에서 도는 코드를 비밀로 만들어 주지 않는다.

제작자에게 이 사실을 말하는 문구는 저작 표면이 갖는다
(`apps/web/src/features/runtime-studio/runtime-copy.ts`의 `confidentiality`). 비밀번호·
API 키·서버 토큰을 코드에 넣지 말라고 적고, 난독화·서버 실행·암호화 같은 **없는 대안을
암시하지 않는다.** 런타임 API는 애초에 그런 비밀에 접근하지 못한다.

## 4. 요청의 런타임 축은 판별 합집합이고 **생략이 세 번째 뜻이다**

```text
필드가 없다(undefined)   말하지 않았다 — 갱신에서 지금 발행된 런타임을 **그대로 둔다**
mode: "disabled"         껐다 — 발행된 런타임을 지운다(저작 소스는 기기에 남는다)
mode: "source"           소스 한 벌. 서버가 컴파일한다
```

첫째와 둘째를 가르는 것이 이 계약의 요점이다. 웹·iOS·안드로이드가 동시에 배포되지 않는
이상 롤아웃 중에는 이 축을 모르는 클라이언트가 갱신 발행을 보내고, 그 부재를 "껐다"로
읽으면 **갱신 한 번이 이미 발행된 런타임을 조용히 지운다** — 제작자는 자기가 하지 않은
일을 당한다.

`applyStoryRuntimePlan`의 `preserve` 갈래가 **아무 문장도 내지 않는 것**이 그 집행이다.

## 5. 저작 소스를 서버가 보관하지 않는다

소스는 컴파일 입력으로 요청 하나를 건너올 뿐이다. 커밋되는 것은 아티팩트와 그 신원뿐이고,
`mainTsx`·`runtimeSourceFiles`·`draftRuntimeFiles` 같은 컬럼을 만들지 않는다.

내구 저작 원본은 기기의 로컬 우선·E2EE 저작 시스템에 그대로 남는다 — 서버가 그것을
보관하기 시작하면 제작자의 원고가 평문으로 DB에 쌓이고, 그건 이 제품이 저작에 대해 한
약속의 반대다.

## 6. 순서 — 컴파일이 트랜잭션 **밖**이고 DB보다 **앞**이다

```text
인증 · 계약 검증
런타임 소스의 모양·상한 검사        경로 · 확장자 · 중복 · 파일 수 · **총 바이트**
컴파일                              수백 ms — 여기까지 DB를 만지지 않는다
아티팩트 검증 · 크기 상한
─────────────────────────────────  발행 트랜잭션 시작
작품 upsert(잠긴 행)
story_media 참조 동기화
story_runtime upsert · delete · **보존**
─────────────────────────────────  커밋
```

**앞인 이유는 실패의 방향이다.** 컴파일이 거절되면 작품 행에 아무것도 쓰이지 않고, 이미
발행된 작품과 그 런타임은 한 글자도 바뀌지 않는다.

**밖인 이유는 시간이다.** TypeScript 프로그램 하나를 세우는 데 수백 밀리초가 들고(실측:
파일 201개 콜드 307ms) 그동안 커넥션과 잠금을 쥐고 있으면 이 발행과 무관한 요청이 함께
느려진다 — 표지 정규화가 같은 자리에서 같은 판단을 했다.

## 7. 상한

저작 상한(`@rowcat/authoring`의 `RUNTIME_PROJECT_LIMITS`)은 파일 **하나**와 파일 **수**를
막는다. 그 둘을 곱하면 이론상 40MB짜리 프로젝트가 규칙을 어기지 않고 성립하고, 그것을
컴파일하는 일은 API 프로세스의 메모리를 통째로 가져간다.

```text
소스 총 바이트     2 MiB      요청 · 컴파일 예산 · 실제 프로젝트(템플릿은 수 KB) 사이
아티팩트 바이트     8 MiB      방출은 소스보다 크다(JSX 변환 + 소스맵)
진단 개수          50         나머지는 잘린 수로만 말한다
진단 문장          500자
```

**서버가 저작 상한을 다시 본다** — 그 판정이 브라우저에서 일어났기 때문이다. 느슨한
사본을 만들지 않는 것이 규칙이라, 서버가 읽는 값은 `@rowcat/authoring`의 **같은 상수**다.

## 8. 저장되는 것

```text
story_runtime
  story_id                 PK · story.id → cascade
  artifact                 jsonb — 컴파일된 아티팩트 그대로
  artifact_format_version  RuntimeArtifact.formatVersion
  runtime_api_version      RuntimeArtifact.apiVersion
  compiler_version         RuntimeArtifact.compilerVersion
  source_hash              제작자 소스의 정본 해시 — **기기의 신원이 들어오지 않는다**
  capabilities             text[] — 컴파일 그래프에서 파생된 능력 가족
  updated_at
```

메타데이터 넷이 컬럼인 이유는 **호환을 묻는 질의가 jsonb를 파싱하지 않아야** 하기
때문이다. "지금 런타임 API 판으로 돌릴 수 없는 발행본이 몇 개인가"는 API 판을 올리는 날
반드시 묻게 되는 질문이고, 그때 TOAST를 통째로 읽는 질의를 쓰게 두면 그 조사가 운영
사고가 된다.

**회원·제작자로 가는 외래키가 없다.** 제작자가 탈퇴해도 공개 작품은 신원만 떼고
남고(`story.owner = null`), 그때 그 작품의 런타임도 남아야 한다 — 그 작품을 하던 사람의 재생이
남의 탈퇴로 사라지면 안 된다(`story_media`가 이미 같은 판단을 했다).

**수명주기 전이는 이 행을 건드리지 않는다.** 공개 → 비공개·링크 공개·보관 어느 것도 작품
행을 지우지 않으므로 아티팩트는 그대로 남고, 복원한 작품은 다시 그 코드로 돈다.

## 9. 능력 매니페스트는 **서버가 파생시킨다**

```text
capabilities: ["generation"]
```

제작자가 스스로 선언하지 않는다. `usesGeneration: false`를 요청에 실을 수 있으면 신뢰된
AI 고지 없이 생성을 부르는 발행본이 만들어지고, 그때 누군가의 키가 사용자가 아무것도
승인하지 않은 채 쓰인다.

판정은 컴파일 결과의 **모듈 그래프**에서 한다 — 런타임 내장을 import한 모듈의 방출 코드에
공개 훅 이름이 남아 있는지 본다. 별칭 import(`useGeneration as useAi`)도 그 코드에는 원래
이름의 프로퍼티 접근으로 남으므로 함께 걸린다.

**이 값은 보안 권위가 아니다.** 실제로 무엇을 부를 수 있는지는 호스트의 능력 표가 정하고,
이 목록이 하는 일은 그보다 **앞에** 서는 것 하나다(고지).

## 10. 실패

```text
제작자 소스의 진단        400 · story_runtime_invalid · StoryRuntimePublishFailure
상한·모양 위반            같은 봉투(화면이 한 목록으로 그린다)
컴파일러·서비스의 실패     500 — 진단으로 접지 않는다
```

마지막 줄이 규칙이다. 컴파일러가 던지는 것은 **우리 실패**이고, 그것을 진단으로 접으면
서버 사고가 문법 오류로 보여 제작자가 자기 코드를 고치려 든다.

진단에 실리는 것은 코드·심각도·문장·**프로젝트 안의 경로**·줄·열뿐이다. 서버 파일 경로·
TypeScript 내부·스택·던져진 예외 문자열은 어느 갈래에서도 나가지 않는다.

**조용히 대화 작품으로 발행하지 않는다.** 제작자는 런타임을 명시적으로 켰고, 그것을 빼고
올리면 자기가 만들지 않은 제품이 카탈로그에 선다(상황 이미지가 같은 판단을 했다).

## 11. ⚠️ 앞으로 `RUNTIME_API_VERSION`을 올릴 때

**이 판이 발행된 아티팩트를 처음으로 내구 제품 데이터로 만든다.**

지금까지 API 판을 올리는 일은 아무것도 깨뜨리지 않았다 — 저장된 아티팩트가 없었고, 모든
아티팩트는 컴파일할 때마다 새로 만들어졌다. 그 전제가 이 슬라이스에서 사라진다.

호스트의 아티팩트 검증은 **정확한 일치**를 요구한다(`apiVersion` · `compilerVersion` ·
`formatVersion`). 그래서 판을 올리는 커밋은 다음 중 하나를 **함께** 가져와야 한다:

```text
① 하위 호환 샌드박스      옛 판을 함께 실을 수 있게 한다
② 재컴파일 이관           story_runtime을 훑어 다시 컴파일한다 — 소스가 서버에 없다(§5)
③ 명시적 호환 계획         무엇이 재생 불가가 되고 제작자에게 무엇을 말하는가
```

②가 지금 불가능하다는 사실이 중요하다 — 소스는 기기에 있고 서버는 그것을 읽지 못한다.
그러므로 실질적인 답은 ①이거나, 제작자에게 **다시 발행하라고 말하는** ③이다.

**오늘은 그 계획이 필요하지 않다.** 이 판 전에 발행된 런타임이 하나도 없으므로 지금 판
하나를 지원하는 것으로 충분하다. 그 사실이 다음 판에서 바뀐다는 것을 여기 적어 둔다.

## 12. 마이그레이션

```text
테이블 하나        story_runtime
컬럼 하나          notification 아님 — 이 슬라이스에는 다른 테이블 변경이 없다
엔드포인트 하나     GET /v2/stories/:id/playback
계약 필드 둘        StoryPublishRequest.runtime · StoryDto.playMode
```

동기화 프로토콜도 `SYNC_PROTOCOL_VERSION`도 봉투 버전도 `AUTHORING_SCHEMA_VERSION`도
`RUNTIME_API_VERSION`도 `RUNTIME_ARTIFACT_FORMAT_VERSION`도 Dexie도 SQLite도 한 글자
바뀌지 않았다. **백필도 없다** — 이 판 전에는 발행된 런타임이 없었으므로 `story_runtime`이
비어 있는 것이 곧 정확한 상태이고, 기존 작품은 전부 `playMode: "chat"`이다.

## 13. 발행 컴파일의 몫 — 회원 하나에 하나

- **컴파일 자리는 프로세스 전체에 둘이고, 한 회원은 그중 하나만 갖는다.** 두 번째 컴파일은 줄을 서지 않고 409
  (`story_runtime_compile_in_progress`)로 돌아간다 — 줄을 세우면 다음 빈자리가 그 회원의 것이 된다. 런타임 소스를
  싣는 발행은 회원 단위 속도 제한(`storyRuntimeCompile`, 10회/10분)을 컴파일 **앞에서** 센다. 그 제한은 저장소가
  응답하지 않으면 열린다 — 메모리는 자리 수와 회원 상한이 이미 묶는다.
- **떠난 요청은 자리를 놓는다.** 요청의 신호가 컴파일까지 닿아 대기열에서 빠지거나 스레드를 끝내고, 자리는 스레드가
  실제로 끝난 뒤에(`exit`) 돌아온다 — 결과를 안 순간 돌려주면 끝나 가는 스레드의 힙과 다음 컴파일의 힙이 겹친다.
- **스택 넘침도 원본이 자원을 다 쓴 것이다**(`runtime_compile_exhausted`). 몇 KB의 중첩 괄호가 TypeScript의 재귀
  파서를 넘친다.
- **갱신은 존재 · 소유 · 출처 · 보관을 먼저 묻고 컴파일한다.** 반대 순서에서는 남의 작품 id에 대한 PUT이 404를 받기
  전에 컴파일 자리를 썼다.
- **삼중 슬래시 참조는 정책이 거절하고, 서버의 라이브러리 집합은 스튜디오와 같다.** `/// <reference lib="dom" />`
  한 줄이 서버 컴파일에 DOM 전역을 되돌렸다. 더 많이 거절하는 변경은 `RUNTIME_COMPILER_VERSION`을 올리지 않는다.
- **`node_modules/`와 `.rowcat/`은 프로젝트 경로의 첫 조각으로 쓸 수 없다** — 컴파일러의 가상 파일 시스템이 그 자리에
  자기 파일을 둔다.
