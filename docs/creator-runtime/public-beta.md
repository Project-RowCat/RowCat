# 크리에이터 런타임 공개 베타

**제품 단계를 나타내는 낱말 하나와, 그 낱말이 지는 약속.** 이 문서는 새 기능을 정의하지
않는다 — 이미 서 있는 런타임을 *바깥 사람이 쓸 수 있는 상태*로 넘기는 경계만 적는다.

```text
공개 베타 = 제품 라벨      이미 있는 발행·재생·조정 경계를 그대로 쓴다
공개 베타 ≠ 두 번째 백엔드  베타 전용 발행 경로도, 런타임 전용 공개 작품 표도 없다
```

## 1. 상태를 말하는 자리가 셋이다

```text
스튜디오 머리말        Runtime Studio 옆의 배지     코드를 쓰는 동안 보인다
시작 템플릿 갤러리     제목 옆의 배지               만들기 **직전** — 가장 값싼 자리다
공개 문서의 첫 장      배지 + 호환성 한 줄          검색으로 들어온 사람이 읽는다
```

값은 `apps/web/src/lib/runtime-beta.ts` 하나에서 온다. 표면마다 낱말을 따로 적으면 같은
제품이 세 이름을 갖고, 그중 어느 것이 공식인지는 아무도 답할 수 없다.

**재생 화면에는 서지 않는다.** 이 배지는 제작자에게 하는 말이다 — 플레이어가 여는 작품에
`베타`를 붙이면 그 작품이 미완성이라는 뜻으로 읽히고, 그것은 제작자가 발행한 작품에 대해
우리가 할 말이 아니다. `runtime-beta.test.ts`가 그 부재를 값으로 지킨다.

**참조 문서 스물다섯 장에 배지를 달지 않는다.** 넷째 장부터는 읽히지 않으면서, API 한 장
한 장이 잠정적이라는 뜻만 남는다 — 잠정적인 것은 이 제품의 단계이지 `useStoryState`의
서명이 아니다.

## 2. 호환성 약속 — **집행되는 것만 적는다**

⚠️ 이 절에서 가장 쉬운 잘못은 **과잉 약속**이다.

```text
호스트의 아티팩트 검증   apiVersion이 **호환 창 안**     packages/runtime/src/declarations/index.ts
                        RUNTIME_API_MIN_COMPATIBLE_VERSION..RUNTIME_API_VERSION · runtimeApiCompatibility
서버에 저작 소스 없음    재컴파일 이관이 불가능하다      docs/creator-runtime/publication.md
```

한동안 첫 줄은 **정확히 일치**였고, 그때는 `RUNTIME_API_VERSION`이 오르는 순간 이미 발행된
작품이 제작자가 다시 발행하기 전까지 열리지 않았다. 지금은 창이 있다 — 4 → 5부터의 판
올림이 전부 더하기였다는 사실(옛 아티팩트가 쓰는 이름은 새 런타임에 그대로 있고, 옛
아티팩트가 내는 패치는 새 렌더러의 표 안에 있다)을 근거로 창 안의 옛 판은 **변환 없이**
돈다. 어댑터가 항등인 것이 창의 조건이다: 이름이 사라지거나 뜻이 바뀌는 판 올림은 창의
아래 경계도 함께 올려야 하고, 그 커밋이 곧 재발행 절차와 함께 오는 커밋이다.

창은 네 소비자(웹 미리보기 워커 · 웹 재생 워커 · 네이티브 하네스 · 서버)가 **한 함수**로
판정한다 — 각자 적으면 한 곳만 창을 열고, 그 어긋남은 "스튜디오에서는 돌고 발행하면 열리지
않는 작품"으로만 드러난다. 그래도 "무슨 일이 있어도 발행본은 계속 돕니다"는 지킬 수 없다:
창을 좁히는 변경이 실제로 있을 수 있고, 그때는 아래의 절차가 답이다.

반대 방향도 같은 무게다. "언제든 무엇이든 바뀔 수 있습니다"는 **사실이 아니고**(더하는
변경이 기본이다), 그 문장을 읽은 제작자는 작품을 만들지 않는다.

남는 약속은 정확히 둘이다.

```text
지금 공개된 API는 호환을 지키며 넓힌다        더하는 변경이 기본
호환을 깨는 변경이 필요하면 **미리 알린다**   조용히 일어나지 않는다
```

`RUNTIME_BETA.promise`가 그 두 문장이고, 양쪽 방향의 이탈을 테스트가 낱말로 막는다.

### 판 올리기는 제품 결정이지 커밋이 아니다

`RUNTIME_API_VERSION`을 올리는 커밋은 **그 답과 함께 온다.** 더하기만 한 판 올림은 창이 그
답이다(`RUNTIME_API_MIN_COMPATIBLE_VERSION`은 그대로이고, 옛 발행본은 그대로 돈다 —
`bootstrap-session.test.ts`가 옛 판의 아티팩트를 실제로 부팅해 확인한다). 창을 좁히는 판
올림은 제작자에게 다시 발행하라고 말하는 절차와 함께 온다. 답 없이 창을 좁히면 이미 발행된
작품이 열리지 않는다. 이 규칙은 공개 베타가 시작되는 순간부터 값을 갖는다(그 전에는 발행된 작품이 없어
비용이 0이었다).

### 베타를 열기 전에 아쉬운 축을 남기지 않는다

그래서 **7이 베타 직전의 마지막 판**이다. 플래그십을 브라우저에서 실제로 눌러 보다 걸린
스타일 축 다섯(`minWidth`·`maxWidth`·`minHeight`·`maxHeight`·`shrink`)을 여기서 함께
열었다 — 알면서 남겨 두면 그 축은 베타가 열리는 순간 **영원히 비싸진다**(그때부터는 축
하나를 여는 데 재발행 절차가 통째로 따라온다).

이후의 판 올림은 그 값을 치른다. 다음에 이 값을 만지려는 사람은 위의 두 답 중 하나를
먼저 갖고 와야 한다.

## 3. 공개 베타 점검 목록

```bash
pnpm runtime:public-beta:check
```

생성물 여섯의 드리프트와 런타임 패키지 여덟의 테스트를 한 번에 지난다. **오케스트레이션일
뿐 판정을 다시 적지 않는다** — 각 검사의 논리는 원래 자리에 그대로 있다.

이 명령은 저장소 전체 건강을 대신하지 않는다.

```bash
pnpm check && pnpm typecheck && pnpm test && pnpm test:e2e && pnpm build
```

### 손으로만 확인되는 것

자동화가 답하지 못하는 축이 남는다. **하지 않은 확인을 했다고 적지 않는다.**

한동안 이 목록의 일곱 줄은 전부 손의 것이었다. 그중 몇은 **사슬이 서 있는가**와 **그것이
좋은가**가 섞여 있었고, 앞의 절반은 여정 21이 답한다. 그래서 두 표로 갈라 둔다 — 섞어 두면
"자동화가 있으니 됐다"로 읽혀 뒤의 절반이 영영 확인되지 않는다.

```text
자동으로 확인된다 (여정 21)
  ✓ UI만 써서 초안 → 런타임 → 템플릿 → 스튜디오 → 코드 → 미리보기 → 발행 → 플레이까지 간다
  ✓ 문서로 가는 링크가 스튜디오 머리말에 **있다**
  ✓ 컴파일 오류가 `Problems`에 서고, 그 줄을 누르면 그 소스로 간다
  ✓ 고치면 자격이 돌아오고 미리보기가 다시 돈다
  ✓ 발행 성공이 **작품 상세로의 이동**으로 관찰된다
  ✓ 발행된 런타임 작품의 주 행동이 `플레이`이고 그 코드가 화면이 된다
```

**남은 것은 전부 사람의 판단이다. 값 테스트가 답할 수 없다.**

```text
[x] 처음 여는 제작자가 시작 화면에서 다음에 할 일을 안다      2026-09-07 · 아래 ①
[x] 문서 링크가 눈에 **띈다**(있는 것과 보이는 것은 다르다)   2026-09-07 · 아래 ②
[x] 시작 템플릿 여섯이 넓은 화면에서 제대로 보인다            2026-09-07 · 아래 ③
[~] 시작 템플릿 여섯이 좁은 화면(재생)에서 제대로 보인다       2026-09-07 · **웹 390px만** · 아래 ③
[ ] 컴파일 오류 **문구**를 읽고 무엇을 고칠지 알 수 있다
[x] 발행 성공이 **분명하게 느껴진다**                          2026-09-07 · 아래 ④
[ ] 발행된 런타임 작품이 보통의 RowCat 작품처럼 느껴진다
```

**① 처음 여는 화면** — 안내 줄이 세 줄로 다음에 할 일을 순서대로 말한다(`src/main.tsx`부터 ·
미리보기에서 실행 `⌘Enter` · 오류는 `Problems`). **그런데 그 둘째 줄이 가리키는 칸이 화면에
없었다** — 미리보기가 기본으로 꺼져 있었고, 그 기본값의 근거는 *"실행 엔진이 없어 그 칸이
빈 문장 하나만 그린다"*였다(같은 자리에 *실행 엔진이 생기면 다시 판단한다*고 적혀 있었고,
그 조건은 이미 충족됐다). 1280px에서 실제로 열어 확인한 뒤 기본값을 켜는 쪽으로 바꿨다
(`runtime-workspace-state.ts`). 대가는 편집기 폭이다 — 1280px에서 `앱 사이드바 240 + 탐색기
240 + 편집기 ~360 + 미리보기 340`이 되고, 끄는 길은 머리말의 스튜디오 메뉴에 그대로 있다.

**② 문서 링크** — 스튜디오 머리말과 안내 줄 **양쪽**에 서 있다(안내 줄을 닫아도 머리말의
것이 남는다). 머리말 쪽은 글리프 하나(`BookOpen`)라 그 줄에서 특별히 두드러지지는 않지만,
처음 여는 사람이 보는 화면에서는 안내 줄의 **글자 링크**가 함께 서므로 이 줄을 통과로 본다.

**③ 템플릿 여섯** — `/runtime-template-lab`(개발 빌드 전용)에서 여섯을 전부, 넓은 폭과
390px 양쪽으로 열어 보았다. **한 건이 실제로 깨져 있었다**: `Messenger`의 `전송` 버튼이
`grow: 1`인 입력 옆에서 자기 라벨보다 좁게 눌려 `전`/`송` 두 줄이 되었다(폭과 무관하게
언제나). 제작자가 피해 갈 방법이 없어서(`ButtonProps`에 `style`이 없다) 렌더러 둘의
예외 목록에 버튼을 더했다 — 그 경위는 `runtime-renderer-web/src/theme.ts`가 갖는다.
나머지 다섯은 두 폭 모두 이상 없다. ⚠️ **네이티브 재생의 좁은 화면은 확인하지 않았다** —
이 줄이 `[~]`인 이유이고, 그 확인에는 시뮬레이터나 기기가 필요하다.

**④ 발행 성공** — 버튼이 도는 동안 스피너와 문구로 바뀌고, 끝나면 **그 작품의 상세**로
간다(`비공개` 배지 · `by 개발자 · 내 작품` · 주 행동이 `플레이`). 축하 모달도 배너도
필요하지 않다 — 도착한 화면이 이미 "무엇이 발행되었고 누가 볼 수 있는가"를 말한다.

### `/runtime-template-lab` — 템플릿 여섯을 한 자리에서

```text
개발 서버 → /runtime-template-lab → 템플릿 하나를 고르면 그것이 돈다 → `좁은 폭(390px)` 토글
```

제품 미리보기와 **같은 컴파일러·같은 QuickJS 호스트·같은 렌더러**로 돌고, 소스는 제품이
초안에 심는 값 그대로다(`instantiateRuntimeTemplate`). 줄이는 것은 **설정뿐**이다 — 제품
경로로 여섯을 보려면 템플릿마다 초안을 새로 만들어야 하고(갤러리는 런타임을 처음 켤 때만
선다), 그 절차 때문에 위의 두 줄이 점검할 때마다 미뤄졌다.

⚠️ **개발 서버에서 첫 컴파일은 1분 넘게 걸린다.** Vite dev가 TypeScript 컴파일러를 번들
없이 실어 나르기 때문이고(요청 4,000건 남짓), 두 번째부터는 십여 초다. `compiling`에서
멈춰 보이면 대개 기다림이지 고장이 아니다 — 다른 파일을 고쳐 HMR이 돌면 그 세션은 버려지고
처음부터 다시 시작한다.

## 4. 여정 21이 지키는 구간

```text
여정 18   스튜디오 **안**에서 끝난다      미리보기가 돌면 통과
여정 20   씨앗이 심은 픽스처를 **연다**   발행은 db:seed:e2e가 이미 했다
여정 21   그 사이의 구간                  제작자가 자기 손으로 낸다
```

```text
초안 → 런타임 켜기 → 템플릿 → 스튜디오 → 코드 → **일부러 틀린다** → 진단 → 그 자리로
     → 고친다 → 미리보기 → 편집기 → 제목 → 발행 → 카탈로그의 작품 → 플레이 → 그 코드가 화면이 된다
```

한가운데의 네 걸음이 나중에 붙었다. 그것 없이는 이 여정이 "옳은 코드가 발행된다"만 보고,
제작자가 실제로 가장 자주 지나는 구간(틀리고 고치는 길)은 아무 값도 지키지 않는 채로
남는다 — 진단이 `Problems`에 닿지 않거나 줄이 눌리지 않아도 전부 초록이다.

값 테스트가 아무리 많아도 "제작자가 UI만 써서 자기 작품을 세상에 낼 수 있는가"에는 답하지
않는다. 그 사슬 중 어디가 끊겨도 값 테스트는 전부 초록이고 제작자는 작품을 낼 수 없다.

⚠️ **이 여정은 포트 3011을 쓴다**(생성 대역). 같은 포트를 쓰는 다른 프로세스가 떠 있으면
Playwright는 그것을 재사용하고, 모든 여정의 가입이 404로 죽는다 — 실패 문구가 대역을
가리키지 않아 원인을 찾기 어렵다.

## 5. 이 단계에서 하지 않는 것

```text
Presence · 등장/퇴장 수명
Overlay · Dialog · Popover · Sheet · Tooltip
스프링·키프레임·제스처·레이아웃 측정
원격 오디오 · 비디오
파일 시스템 · 네트워크 · 임의 npm · DOM · 타이머
```

이 목록은 **날짜를 암시하지 않는다.** 공개 문서에 옮기지 않는 이유가 그것이다 — 없는
기능의 이름을 읽은 제작자는 그것을 기다린다.
