# 보안 검토 기록

> 기록 문서다. 공개 베타 전에 한 영역씩 독립 검토를 하고, 무엇을 봤는지·무엇을 고쳤는지·무엇이 남았는지를
> 적는다. **고치지 않은 것은 공격 순서를 적지 않는다** — 이 문서도 공개된다. 고친 것은 무엇이 막혔는지를
> 적어, 다음 사람이 그 줄을 지우지 않게 한다.

## 인증 · 첫 설정 · 배포 오리진 (2026-10-31)

### 범위와 방법

```text
인증 설정     apps/api/src/auth/*         Better Auth 1.7.2와 플러그인(expo · passkey · two-factor), hooks, 닫힌 경로
계정 래퍼     routes/me/account.ts · services/account/*   비밀번호 설정 · 연결 해제 · 세션 · 패스키
첫 설정       services/setup/* · routes/setup.ts · lib/local-request.ts · auth/local-sign-in.ts · apps/desktop
오리진        lib/origins.ts · app.ts의 CORS · trusted-origins.ts · webauthn-config.ts · 웹의 리디렉션 · 콘솔 CSP
```

1. 세 영역을 서로 모르는 검토자 셋이 읽었다. 라이브러리 동작에 기대는 주장은 설치된 `node_modules`의 코드로
   확인하게 했다.
2. 나온 후보마다 **반박하라고** 지시받은 검증자 셋이 서로 다른 관점(끝까지 실제로 되는가 · 라이브러리가 정말
   그렇게 하는가 · 문서로 정한 결정이고 그 근거가 맞는가)으로 따로 확인했다. 아래 「고친 것」은 셋 모두
   인정한 것이다.

### 고친 것

| 무엇 | 무게 | 처리 |
| --- | --- | --- |
| 비밀번호 설정이 최근 로그인을 묻지 않았다 — 오래된 세션 쿠키 하나가 영구적인 로그인 수단을 만들고 계정을 빼앗을 수 있었다 | 높음 | `setAccountPassword`·`deleteAccountPasskey`가 `requireFreshSession`을 먼저 부른다. 반대를 고정하던 테스트를 근거와 함께 뒤집었다 |
| 로컬 소유자의 두 문이 「이 컴퓨터」를 요청 헤더로만 판단했다 — 같은 컴퓨터에서 헤더 없이 전달하는 도구를 거치면 원격 요청도 통과했다 | 중간 | `LOCAL_OWNER_ENABLED=on`(데스크톱 설치본만 켠다)이 없으면 두 문이 닫힌다. `Origin`도 루프백 호스트여야 한다. 데스크톱 README가 포트를 다른 기기에 열지 말라고 적는다 |
| 비밀번호 재설정 링크가 앱의 커스텀 스킴으로 돌아갈 수 있었다 | 중간 | `password-reset-policy.ts` — 재설정의 두 문은 `http(s)`나 상대 경로만 받는다. 앱은 재설정을 웹에 넘기므로 깨지는 흐름이 없다 |
| 로그인 리미터가 클라이언트가 보낸 `X-Forwarded-For`로 셌다(기본 compose 모양) | 중간 | `lib/client-ip.ts` — 주소를 소켓에서 정하고 라이브러리에는 우리가 넣는 헤더 하나만 읽게 했다. 전달 헤더는 `AUTH_TRUSTED_PROXIES`의 피어에게서만 믿는다 |
| 아무도 부르지 않는 라이브러리 경로가 열려 있었다(`/verify-password` 등 넷) | 낮음 | `auth/http-surface.ts`의 닫힌 목록에 더했다 |
| 콘솔 컨테이너의 오리진 검사가 줄 단위였다 | 정보 | 줄바꿈이 든 값을 먼저 거절한다(`apps/admin/docker/rowcat-runtime-config.sh`). 운영자 값이고 전에도 컨테이너가 멈추는 쪽이었다 |

### 남은 결정 — 운영자 · 모바일

- **네이티브 로그인의 세션 전달.** 앱의 브라우저 로그인은 세션을 `rowcat://` 딥링크로 앱에 넘긴다(`@better-auth/expo`의
  방식). 커스텀 스킴은 어떤 앱이 받는지를 증명하지 않으므로, 그 전달을 검증된 https App Link / Universal Link나 앱이
  교환하는 일회용 코드로 바꾸는 것이 남은 일이다. 네이티브 재빌드·도메인 연결 파일·플러그인 변경이 따르는
  모바일 아키텍처 결정이라 이번에 고치지 않았다. 서버 쪽에서 경로를 고정하는 것은 도움이 되지 않는다는 점까지
  검증했다(`auth/http-surface.ts` 헤더).
- **웹의 CSP는 report-only다**(`apps/web/vite.config.ts`). 하이드레이션의 인라인 스크립트에 nonce가 없어서다. 웹의
  XSS 하나가 그 오리진의 동기화 키와 BYO 키에 닿는다는 뜻이고, 알려진 공백으로 적어 둔다.
- **로컬 소유자의 비밀번호 설정.** 이제 비밀번호 설정은 최근 로그인을 요구하는데, 로컬 소유자는 로그아웃이 없고 같은
  세션이 30일 간다. 그래서 첫날이 지나면 계정 화면의 비밀번호 설정이 「다시 로그인하라」에서 멈춘다. 검사를 풀지
  않았다 — 로컬 소유자의 쿠키가 비밀번호를 얻으면 이 컴퓨터 밖에서 로그인되는 관리자가 생긴다. 남은 일은 그
  화면이 로컬 소유자에게 해당 없는 칸(이메일·비밀번호·로그인 수단)을 그리지 않는 것이다(이미 알려진 미완).
- **프록시 뒤 배포의 설정 변경.** 전달 헤더를 목록에 있는 연결에게서만 믿게 되면서, CDN 대역만 적고 그 사이에 호스트
  프록시를 둔 배포는 그 프록시의 주소도 적어야 한다(`docs/ops/CONFIGURATION.md` §프록시 뒤). 그 모양이면 API가 한 번
  경고한다.
- **이전에 남긴 것**(동기화 푸시의 키 소유 증명, 연령 게이트, 관리형 생성 입력 크기 등)은 이 범위 밖이고 그대로다.

### 확인했고 문제없던 것

- CORS는 정확한 집합 비교이고 와일드카드·`null`·알 수 없는 오리진을 되돌려 주지 않는다. 오리진 목록은 `URL.origin`으로
  접어 대소문자·끝 슬래시·기본 포트 차이를 없앤다.
- 로그인 후 돌아갈 주소(`redirect`, `settings-return`, 콘솔의 `safeReturnPath`)는 `//`, `/\`, 제어 문자, 인코딩된
  구분자를 거절한다. 메일 링크와 콜백은 요청의 `Host`가 아니라 설정된 `API_ORIGIN`에서 만든다.
- 첫 설정 코드는 60비트 HMAC이고 비교는 상수 시간이다. 시도는 요청을 읽기 전에 세고, 완료 뒤에는 코드를 보지
  않는다. 코드는 로그 한 줄 밖으로 나가지 않는다.
- 2FA 도전은 비밀번호 로그인에만 서고, 다른 비밀번호 입구(사용자명·전화·매직 링크 등)를 여는 플러그인이 없다.
  신뢰 기기 요청은 거절된다.
- 쿠키는 `httpOnly`·`SameSite=Lax`·운영에서 `Secure`이고, 도메인은 `AUTH_COOKIE_DOMAIN`에서만 온다.

### 다시 하기

같은 세 영역을 세 갈래로 나눠 읽고, 후보마다 반박하는 검증을 둔다. 라이브러리를 올리면 `auth/http-surface.ts`의
닫힌 목록을 새 버전의 라우트 목록과 다시 맞춘다 — 새 경로는 기본으로 열린다.

## 암호화 동기화 · 페어링 · MCP 기기 (2026-10-31)

### 범위와 방법

```text
서버       services/sync/* · routes/me/sync.ts · db/tables/sync.ts · app.ts의 onError
프로토콜   packages/sync — 봉투 · 키링 · 엔진 · 컨트롤러 · 페어링 · 코덱
클라이언트 apps/web/src/lib/local-sync/* · lib/local-data/* · apps/mobile의 같은 자리
MCP 기기   apps/mcp — 설정 파일 · 페어링 · 기기 · 경계 검사
```

앞 절과 같은 방법이다. 서로 모르는 검토자들이 읽고, 후보마다 세 검증자가 반박을 시도했다. 그 뒤 「무엇이 빠졌는가」를
묻는 검토자 하나가 범위를 다시 훑었고, 거기서 나온 후보도 같은 세 갈래 검증을 거쳤다. 고친 다음에는 그 변경 자체를
다른 검토자 셋이 다시 읽고 같은 방식으로 검증했고(13건 모두 인정), 그 수정을 두 번 더 같은 방식으로 읽었다(9건 인정
1건 반박, 그다음 11건 인정 — 그중 둘은 같은 결함). 인정된 것은 모두 이 절의 처리에 반영했다. 아래 「고친 것」은 셋
중 둘 이상이 인정한 것이다.

### 고친 것

| 무엇 | 무게 | 처리 |
| --- | --- | --- |
| 당겨 오기 한 페이지에 바이트 상한이 없었다 — 행 수 상한만으로는 한 응답이 수백 MB가 될 수 있었고, 동시 요청 몇 개로 API 프로세스의 힙이 바닥났다 | 높음 | `SYNC_LIMITS.pullMaxBytes`(8 MB). 크기만 먼저 읽어 페이지 끝을 정하고 그다음에 본문을 읽는다. 첫 행은 크기와 상관없이 항상 나가서 커서가 멈추지 않는다. 두 읽기 사이에 행이 다시 쓰여 빈 페이지가 나오면 다시 읽고, 그래도 비면 한 문장으로 한 행을 읽는다 — 빈 페이지는 엔진에게 「커서가 안 움직였다」로 읽혀 실행이 멈춘다. 클라이언트는 이미 `hasMore`로 돈다 |
| 다른 탭이 다른 계정으로 로그인하면, 열려 있던 탭이 이전 계정의 키를 들고 새 계정의 세션으로 동기화했다 — 이전 계정의 커서가 새 계정의 순번으로 건너뛰어 자기 기록을 영영 건너뛰었고, 새 기록은 남의 공간에 올라갔다 | 중간 | `@rowcat/sync` 컨트롤러가 매 실행 전과 설정 · 점검 · 초기화 전에 세션이 누구 것인지(`SyncTransport.sessionOwner`, `/me`)와 세션의 키링이 이 키로 열리는지를 묻는다. 남의 세션이면 「다시 로그인」으로 실패하고 키는 잊지 않는다. 주인의 세션인데 키링이 바뀌었으면(다른 기기나 탭에서 초기화) 저장된 키로 시작할 때처럼 다시 점검한다 — 기기 키는 그 회원의 모든 탭이 함께 쓰는 한 행이라, 다른 탭이 방금 저장한 키를 먼저 판단하고, 잊기 직전에 다시 읽는다. 판단이 나기 전까지 메모리의 키는 그대로 두어, 점검이 도중에 실패해도 다음 실행이 다시 묻는다. 묻는 데 실패하면 그 실행이 실패한다. 시작 점검에서 남의 세션을 만난 탭은 포커스 같은 신호마다 다시 점검한다(자동 동기화가 꺼져 있어도 점검은 한다). 웹·모바일이 같은 컨트롤러를 쓴다 |
| 한 탭에서 「이 기기 데이터 지우기」나 탈퇴를 하면, 같은 회원의 다른 탭이 지워진 데이터베이스를 조용히 다시 만들었다 — 동기화가 켜진 탭은 지운 내용을 평문으로 다시 받아 왔다 | 중간 | 활성 연결이 `versionchange`(삭제)를 받으면 자동 재열기를 끈 채 닫고 탭을 새로 고친다(`lib/local-data/db.ts`). 업그레이드는 Dexie의 기본 동작 그대로다 |
| 멱등 키 행이 회원당 끝없이 쌓였다 — 충돌만 내는 밀어 넣기는 할당량에 잡히지 않으면서 행을 남겼다 | 중간 | `SYNC_LIMITS.idempotencyMaxPerOwner`(1,000). 새 키를 잡을 때 그 회원의 오래된 행을 넘치는 만큼 지운다. 실제 재시도가 쓰는 것은 최근 몇 개다 |
| DB 문장이 실패하면 오류 로그에 바인딩 값이 그대로 남았다 — 동기화 쪽은 키링 · `auth_key` · 페어링 봉투 · 암호문, 인증 쪽은 세션 토큰 · 비밀번호 해시 · 확인 값. 풀 고갈이나 재시작 같은 평범한 장애로 충분했다 | 중간 | `lib/loggable-error.ts` — 원인 사슬 어디에든 질의 실패가 있으면 SQL 문(자리표시자만)과 드라이버의 코드 · 메시지만 남긴다. `app.onError`, Better Auth의 로거와 오류 훅, 작업 실행기가 모두 이 함수를 지난다. 인증 오류 훅은 응답도 직접 만든다 — 그냥 돌려보내면 그 밑의 HTTP 라우터가 오류 객체를 그대로 찍는다. 정적 검사는 호출 자리를 읽으므로 라이브러리가 오류 객체 안에 넣는 값은 볼 수 없었다 |
| 깨우기 스트림의 세션 재확인이 하트비트에만 붙어 있어서, 계정이 활발한 동안에는 한 번도 돌지 않았다 | 낮음 | 깨우기 프레임을 보내기 전에도, 마지막 확인에서 하트비트 간격이 지났으면 다시 묻는다 |
| 새 레코드가 하나라도 있는 밀어 넣기마다 회원의 모든 행을 훑어 종류 수를 셌다 | 낮음 | 들어온 종류를 하나씩 찾아보다가 회원에게 없는 종류가 처음 나오면 그때 센다. 한 묶음의 종류가 상한보다 많으면 훑지 않고 거절한다 |
| MCP가 동기화 초기화 뒤의 옛 키로 시작해서, 에이전트에게 「초안 없음」을 사실처럼 보여 줬다 | 낮음 | `serve`와 `doctor`가 시작할 때 쓰는 키가 지금 키링을 여는지 서버에 묻는다(`verifyStoredDek`). 확실히 아니면, 파일의 키이고 다시 읽어도 같은 키일 때만 파일에서 지우고 `pair`를 안내한다(그사이 `pair`가 새 키를 썼으면 그대로 둔다). `ROWCAT_SYNC_KEY`의 키는 파일을 건드리지 않고 그 값을 바꾸라고 안내한다 |
| MCP 설정 파일이 이미 느슨한 권한으로 있으면, 세션과 키가 그 파일에 먼저 쓰인 뒤에야 권한이 좁혀졌다 | 낮음 | 옆에 임의 이름 · `wx` · 0600으로 새 파일을 만들고 이름을 바꿔 덮는다. 디렉터리도 0700으로 좁힌다 |
| MCP의 비밀 로그 검사가 실제 출력 함수(`out` · `status` · `console.*`)를 보지 않았다 | 정보 | 그 호출의 인자를 괄호 균형으로, 문자열 세 형식을 아는 한 번의 읽기로 검사한다. 글은 빼고 템플릿의 식은 남기며, 이름 안의 비밀 단어(`dekBytes`)도 잡는다 |
| 페어링 경로 주석이 「새 요청이 이전 링크를 끊는다」고 적고 있었다(실제로는 열린 세션을 끊지 않는다) | 정보 | 주석을 실제 동작대로 고쳤다. 동작은 바꾸지 않았다 — 열린 세션을 끊는 것은 다른 기기의 페어링을 도중에 취소하는 일이다 |

### 반박된 것

- **설정 도중 소유권이 바뀌면 복구 코드를 버린다.** 서버에 키링이 생긴 뒤 범위가 바뀌면 코드를 돌려주지 않는 것은
  맞다. 그러나 그 키로 올라간 암호문이 없고, 잠긴 화면에 「처음부터 다시」가 있으며, 코드를 돌려주면 다음 계정의
  화면에 이전 계정의 비밀을 보여 줄 수 있다. 셋 모두 지금 방향이 맞다고 봤다.
- **MCP 페어링의 「동기화 미설정」 분기가 맞지 않는다.** 분기는 죽어 있지만 서버가 그 코드를 보내지 않고, 사용자가
  보는 결과도 주장과 달랐다.
- **로그 정리가 드라이버의 메시지를 남긴다.** 메시지가 값을 인용하는 경우가 있다는 주장이었으나, 연결 · 시간 초과 같은
  장애 때의 메시지는 값을 담지 않고, 진단에 필요한 유일한 문장이라 남긴다는 판단이 셋 중 둘이었다.

### 남은 것

- **기록 평문의 압축 해제에 출력 상한이 없다.** 이 계정의 키를 이미 가진 쪽만 만들 수 있는 입력이라 무게를 낮게 봤고
  (셋 중 하나만 인정), 이번에 고치지 않았다.
- **동기화 밀어 넣기에 회원 단위 속도 제한이 없다.** 멱등 행 상한과 할당량이 저장 공간을 막지만 요청 속도 자체는
  막지 않는다. 정책을 더할 때는 부트스트랩(수백 청크)이 걸리지 않는 값이어야 한다.
- **로그인 · 로그아웃이 다른 탭에 알려지지 않는다.** 위의 컨트롤러 검사로 데이터는 지켜지지만, 다른 계정의 세션 아래에
  남은 탭은 포커스 같은 신호가 올 때까지 동기화를 쉰다.
- **Better Auth 어댑터의 대체 조인이 오류를 직접 찍는다.** 세션 조회의 조인 대체 경로가 `console.error`를 스스로
  부르므로 위의 정리를 지나지 않는다. 지금 그 질의의 값은 회원 id와 개수 상한뿐이다. 라이브러리를 올리거나 조인
  설정을 바꾸면 다시 본다.
- **복구 코드 재발급과 페어링 승인에는 세션 주인 검사가 없다.** 둘 다 이 회원에 묶인 증명과 코드 해시를 쓰므로 남의
  세션에서는 서버가 거절한다. 검사를 더하는 것은 다음 일로 남긴다.
- **검사는 실행 앞에 한 번이다.** 한 실행은 여러 페이지와 청크로 이어지고, 실행 도중에 다른 탭이 계정을 바꾸면 그 뒤의
  요청은 바뀐 쿠키를 탄다. 창은 한 실행의 길이로 좁아졌을 뿐 닫히지 않았다. 닫으려면 엔진이 페이지마다 커서를
  쓰기 전에 다시 물어야 한다.
- **이전에 남긴 것**(동기화 밀어 넣기의 키 소유 증명)은 그대로다.

### 다시 하기

같은 네 영역을 나눠 읽고, 빠진 것을 묻는 검토를 한 번 더 둔다. 동기화 응답에 새 필드를 더하면 그 필드가 페이지
바이트 계산(`sync_record.bytes`)에 들어가는지 확인한다.

원격 이미지 프록시 내부와 `/v2/media` 전달은 범위 밖이다(별도 검토). 방법은 앞 절들과 같다 — 영역마다 서로 모르는
검토자가 읽고, 후보마다 세 검증자가 반박을 시도했으며(20건 인정, 9건 반박), 영역 사이의 틈을 묻는 검토자가 한 번 더
훑었다. 고친 다음에는 그 변경을 영역별 검토자와 「원래 발견이 정말 닫혔는가」를 재현 스크립트로 다시 돌리는 검토자가
읽고 같은 방식으로 검증했으며(11건 인정, 10건 반박), 그 수정을 두 검토자가 한 번 더 읽었다(작은 결함 다섯을 더 고쳤다). 아래 「고친 것」은 셋 중 둘 이상이
인정한 것이다.

### 반박된 것

- **원격 자산 목록이 목적지는 묶지만 고르기는 묶지 않는다.** 선언한 주소 중 하나를 상태로 고르면 몇 비트가 나간다는
  것은 이미 문서에 적힌 정적 선언의 대가다.
- **패치 속성 값의 `__proto__` 같은 키.** 검사의 차이는 실제이지만 모든 소비자가 그 값을 이미 막는다.
- **Hermes가 생성 요청을 세션의 허가 없이 실행한다.** 하네스가 허가가 없으면 능력 자체를 설치하지 않는다.
- **네이티브 입력의 자동 완성, 범위 없는 숫자 스타일.** 보안 결과가 없고, 앞의 것은 동작 차이로 남긴다.
- **소유자가 자기 보관 작품을 재생할 수 있다.** 재생 자격의 정의가 그렇고 시험이 있다.
- **생성 능력 감지가 문자열 포함 검사다.** 놓치면 재생이 닫힌 쪽으로 실패한다.
- **MCP 미리보기의 인라인 컴파일, VM 치명 실패의 문구.** 창작자 자신의 코드를 자기 컴퓨터에서 돌리는 경로다(아래 남은 것).
- 두 번째 라운드에서: 경계 검사가 형제 모듈만 걷는다(지금 의존이 그 모양뿐이다), 비정규 경로의 예약 검사(부르는 자리가
  없다), MCP 상한 주석(고쳤다) 등.

### 남은 것

- **멈춘 네이티브 호출은 막히지 않고 끊긴다.** 돌아온 턴은 유예 100ms 안에서, 돌아오지 않는 턴은 생존 확인의 한도(웹
  5초 남짓, 모바일 5초) 안에서 끝난다 — 그동안 그 스레드는 멈춰 있다. 엔진의 문자열 검색을 바꾸는 일은 하지 않았다.
- **MCP Node 호스트에는 생존 확인이 없다.** 그 프로세스는 창작자 자신의 초안을 자기 컴퓨터에서 돈다. 돌아오지 않는
  호출은 stdio 서버를 붙잡는다 — 스레드 경계가 필요하다.
- **네이티브는 이벤트가 깨우는 실행을 확인 문에 세우지 않는다.** 웹과 달리 한 이벤트가 한 조각을 문 밖에서 돈다.
  이벤트의 속도는 사람과 플랫폼이 정한다.
- **실기기에서 재지 않았다.** 하네스 CSP는 헤드리스 Chromium에서만 부팅을 확인했고(iOS의 `file:` 문서 아래 WASM
  가져오기는 시뮬레이터나 기기 확인이 필요하다), 생존 확인이 WebView를 다시 세울 때 붙잡힌 웹 콘텐츠 프로세스가
  실제로 끝나는지, 유예와 한도가 저사양 기기에서 맞는지도 재지 않았다.
- **MP3 길이는 여전히 머리말 추정이다.** 첫 프레임이 뒤 프레임보다 높은 비트레이트를 주장하면 그 차이만큼 길이를 놓친다
  — 모든 프레임을 걷는 일만 닫는다.
- **회원 단위 컴파일 상한은 프로세스마다다.** 복제본이 여럿이면 한 회원이 복제본마다 하나를 가진다. 속도 제한은
  Redis가 있을 때 복제본을 가로지른다.
- **하네스 realm의 같은 오리진 자식 프레임**은 자기 생성자를 갖는다 — WebRTC 제거는 탈출한 코드의 손을 좁히는 것이지
  두 번째 격리가 아니다.
- **`<link rel=preconnect>`가 이 정책에 막히는지**(이름 조회 · TCP · TLS) 안드로이드 WebView와 WKWebView에서 확인하지
  않았다.
- **안드로이드는 멈춘 렌더러 프로세스를 직접 끝내지 않는다.** WebView를 버리고 새로 세울 뿐이다 — API 29 이상의
  `WebViewRenderProcess.terminate()`를 부르는 일은 기기에서 확인할 수 있을 때 한다. 단일 프로세스 WebView(7.x)에서는
  위의 15초 한도가 세션을 끝내지만 멈춘 스레드는 앱을 끝낼 때까지 남는다.

### 다시 하기

같은 일곱 영역을 나눠 읽고 영역 사이를 묻는 검토를 둔다. 하네스 문서나 런타임 호스트가 바뀌면 하네스를 다시 만들고
런타임 세대를 올린다. 런타임 공개 API에 내장 함수가 늘면, 그것이 한 번의 네이티브 호출로 얼마나 오래 돌 수 있는지를
따로 본다.
